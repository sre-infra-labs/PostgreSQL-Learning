# Patroni + etcd PostgreSQL Major-Version Upgrade: 15 to 18

This runbook upgrades the PostgreSQL **primary Patroni cluster** in this
repository from PostgreSQL 15 to PostgreSQL 18. It supports a cluster with two
or more PostgreSQL/Patroni nodes and uses `pg_upgrade --link` on the former
Patroni leader. Replicas are not upgraded with `pg_upgrade`; they are synchronized
from the upgraded primary with PostgreSQL's documented `rsync` procedure.

The procedure has a planned outage. It is intentionally conservative because
the PostgreSQL system identifier changes during a major upgrade and physical
replication cannot continue between PostgreSQL 15 and PostgreSQL 18.

Official references:

- [Patroni: Major Upgrade of PostgreSQL Version](https://patroni.readthedocs.io/en/latest/existing_data.html#major-upgrade-of-postgresql-version)
- [PostgreSQL: pg_upgrade](https://www.postgresql.org/docs/18/pgupgrade.html)

## Scope and topology

This document covers the `primary_cluster` group. In the current inventory it
contains:

| Node | Address | Purpose |
| --- | --- | --- |
| `docpg-cls1-pg1` | `172.18.0.11` | Patroni member; designed leader |
| `docpg-cls1-pg2` | `172.18.0.12` | Patroni member; synchronous standby |
| `docpg-cls1-pg3` | `172.18.0.13` | Patroni member; asynchronous `nosync` replica |

Roles are dynamic. Never assume `pg1` is the leader; identify the current
leader with `patronictl` before stopping services.

Every PostgreSQL container also runs one member of the three-member etcd DCS,
plus Patroni, pgBackRest, pgBouncer, HAProxy, and Keepalived. PostgreSQL data
and logs are in per-node Docker volumes. The pgBackRest repository is the
shared `pg-backups` volume.

The runbook assumes the standard paths generated by this role:

| Item | Value |
| --- | --- |
| Old PostgreSQL data | Discovered from the running source cluster |
| New PostgreSQL data | `/var/lib/postgresql/18/main` |
| Old binaries | Derived from the discovered source major |
| New binaries | `/usr/lib/postgresql/18/bin` |
| Patroni config | `/etc/patroni/patroni.yml` |
| pgBackRest config | `/etc/pgbackrest/pgbackrest.conf` |
| Patroni scope / pgBackRest stanza | `docpg-cls1` |
| PostgreSQL service manager | `patroni.service` |
| DCS | etcd on ports `2379` and `2380` |

If your inventory uses different names, IPs, versions, paths, or stanza names,
replace the examples and verify them before proceeding.

## Critical warnings

1. **This is a planned outage.** Stop application writes and drain connection
   pools before the maintenance window.
2. **Do not run `pg_upgrade` on a physical Patroni replica.** PostgreSQL does
   not support that operation. Synchronize each replica from the upgraded
   primary with the offline rsync procedure in step 12.
3. Stop Patroni on every PostgreSQL node before upgrading the former leader.
   Keep etcd running and maintain quorum. For a two-member etcd cluster, both
   members must remain available; for three members, do not take two etcd
   members down at once.
4. Do not run the installation playbook with `-e reinit_cluster=true`. The
   role removes the configured PostgreSQL data directory, etcd data, and
   Patroni keys. That is not the upgrade procedure.
5. Do not run `playbook-cleanup.yml`, remove Docker volumes, or run
   `delete_old_cluster.sh` before acceptance.
6. Do not start the old and new PostgreSQL clusters at the same time on one
   node. Both clusters must never use the same port or data directory.
7. `pg_upgrade --link` requires the old and new data directories on the former
   leader to be on the same filesystem. It uses hard links, so the old PG15
   directory is **not an independent rollback copy** after PG18 starts writing.
   Keep the logical dumps, pgBackRest backup, and a separate filesystem/volume
   backup until acceptance.
8. With `--link`, do not start any PostgreSQL server after `pg_upgrade` until
   rsync has completed for every standby. Starting PG18 can modify files shared
   with the old directory and makes the old cluster unsafe to start.
9. The cluster DCS state must be removed or its `initialize` key cleared after
   the PG18 primary is prepared. The upgraded cluster has a new system ID;
   retaining the old Patroni initialization key prevents a clean start.

## Execution context

Commands marked **HOST** run in a terminal on the Mac. Commands marked
**CONTAINER** run inside an interactive container shell as `root`. The host has
no mapped PostgreSQL, Patroni, or etcd ports, so container commands must not be
run directly on the Mac.

Enter one container at a time from the Mac when a step says to use a container
shell:

```bash
# HOST — use the node currently identified as the leader
docker exec -it -u root docpg-cls1-pg1 bash
```

For a step that applies to every node, open a separate shell for each node and
run the same **CONTAINER** block in each shell. Do not paste `docker exec`
inside a container shell.

`runuser -u postgres --` means “run the following command as the PostgreSQL OS
user.” The examples assume the interactive shell starts as `root`.

## Optional prerequisite: create an approximately 5 GB `pgbench` database

Run this on the current Patroni leader while the source PostgreSQL cluster is
healthy and replication is operating. The database is created through the
leader, so its contents will also be streamed to the replicas and included in
the backups used by this runbook. Do not run this against an existing database:
`pgbench --initialize` recreates its benchmark tables.

`pgbench` uses a scale factor rather than a target size. A scale of `350` is a
reasonable starting point for approximately 5 GB on this setup, but the actual
size depends on the PostgreSQL version, page layout, indexes, and storage
configuration. Verify the result and adjust the scale before starting the
upgrade if an exact test size is required.

```bash
# CONTAINER — current Patroni leader; run before the maintenance outage
PG_BENCH_DB="pgbench_upgrade_5gb"
PG_BENCH_SCALE=350
PG_BENCH_VERSION_NUM=$(runuser -u postgres -- psql -h 127.0.0.1 -U postgres -Atqc \
  "SHOW server_version_num;")
PG_BENCH_MAJOR=$((PG_BENCH_VERSION_NUM / 10000))
PG_BENCH_BIN="/usr/lib/postgresql/${PG_BENCH_MAJOR}/bin"

test -x "$PG_BENCH_BIN/pgbench"
runuser -u postgres -- "$PG_BENCH_BIN/createdb" \
  -h 127.0.0.1 -U postgres "$PG_BENCH_DB"
runuser -u postgres -- "$PG_BENCH_BIN/pgbench" \
  -h 127.0.0.1 -U postgres --initialize --scale="$PG_BENCH_SCALE" \
  "$PG_BENCH_DB"

runuser -u postgres -- "$PG_BENCH_BIN/psql" \
  -h 127.0.0.1 -U postgres -d "$PG_BENCH_DB" -Atqc \
  "SELECT pg_size_pretty(pg_database_size(current_database())) || ' (' ||
          pg_database_size(current_database()) || ' bytes)';"
```

If the database already exists, stop and either choose a different
`PG_BENCH_DB` name or remove the test database only after confirming that it is
not used by an application:

```bash
# CONTAINER — only for a confirmed disposable test database
runuser -u postgres -- "$PG_BENCH_BIN/dropdb" \
  -h 127.0.0.1 -U postgres "$PG_BENCH_DB"
```

### CONTAINER — discover the source version and define variables

Run this while the existing PostgreSQL cluster is still running. The source
major and data directory are discovered from the live server, so this works
whether the source is PG14, PG15, or another older supported major. Do not edit
the Ansible version variable yet. Keep this shell open, or record the printed
values for any later shell used during rollback.

```bash
# CONTAINER
TARGET_MAJOR=18
# This document is executed in an interactive shell. Do not leave errexit or
# nounset enabled: later checks intentionally use non-zero statuses, including
# `pg_ctl status` returning 3 when the source server is stopped.
set +e
set +u

OLD_VERSION_NUM=$(runuser -u postgres -- psql -h 127.0.0.1 -U postgres -Atqc \
  "SHOW server_version_num;")
case "$OLD_VERSION_NUM" in
  ''|*[!0-9]*)
    echo "Unable to discover a numeric PostgreSQL server_version_num: $OLD_VERSION_NUM" >&2
    echo "Stop here and verify that the source PostgreSQL server is running." >&2
    OLD_VERSION_NUM=0
    ;;
esac
OLD_MAJOR=$((OLD_VERSION_NUM / 10000))
OLD_DATA=$(runuser -u postgres -- psql -h 127.0.0.1 -U postgres -Atqc \
  "SHOW data_directory;")

test "$OLD_MAJOR" -lt "$TARGET_MAJOR"
test -d "$OLD_DATA"
test -f "$OLD_DATA/PG_VERSION"

NEW_DATA="/var/lib/postgresql/${TARGET_MAJOR}/main"
OLD_BIN="/usr/lib/postgresql/${OLD_MAJOR}/bin"
NEW_BIN="/usr/lib/postgresql/${TARGET_MAJOR}/bin"
CLUSTER_NAME="docpg-cls1"
STANZA_NAME="docpg-cls1"
UPGRADE_DIR="/var/lib/postgresql/upgrade-backups/pg${OLD_MAJOR}-to-pg${TARGET_MAJOR}-$(date '+%Y-%m-%d__%H_%M_%S')"

printf 'source=%s target=%s old_data=%s new_data=%s\n' \
  "$OLD_MAJOR" "$TARGET_MAJOR" "$OLD_DATA" "$NEW_DATA"
test -x "$OLD_BIN/postgres"
test ! -e "$NEW_DATA" || test -z "$(ls -A "$NEW_DATA" 2>/dev/null)"
test "$(stat -c %d "$OLD_DATA")" = "$(stat -c %d /var/lib/postgresql)"
install -d -o postgres -g postgres -m 700 "$UPGRADE_DIR"
```

The `test` for `NEW_DATA` must pass. If it does not, stop and determine
whether it is an automatically-created empty PG18 cluster. Never overwrite a
non-empty target without verifying its ownership and purpose. The filesystem
device test must also pass because `--link` cannot link files across
filesystems.

### HOST — find the current leader

### CONTAINER — baseline checks on the current leader

Enter the leader container and run:

```bash
# CONTAINER — run on the current leader
runuser -u postgres -- "$OLD_BIN/psql" -h 127.0.0.1 -U postgres -Atqc \
  "SHOW server_version; SHOW server_version_num; SHOW data_directory;" \
  > "$UPGRADE_DIR/source-settings.txt"
runuser -u postgres -- "$OLD_BIN/psql" -h 127.0.0.1 -U postgres -Atqc \
  "SELECT datname, datcollate, datctype FROM pg_database ORDER BY 1;" \
  >> "$UPGRADE_DIR/source-settings.txt"

runuser -u postgres -- "$OLD_BIN/psql" -h 127.0.0.1 -U postgres -P pager=off -c \
  "SELECT datname, pg_size_pretty(pg_database_size(datname)) AS size
     FROM pg_database ORDER BY pg_database_size(datname) DESC;" \
  > "$UPGRADE_DIR/database-sizes.txt"

runuser -u postgres -- "$OLD_BIN/psql" -h 127.0.0.1 -U postgres -P pager=off -c \
  "SELECT extname, extversion FROM pg_extension ORDER BY 1;" \
  > "$UPGRADE_DIR/extensions.txt"

runuser -u postgres -- "$OLD_BIN/psql" -h 127.0.0.1 -U postgres -P pager=off -c \
  "SELECT client_addr, application_name, state, sync_state,
          sent_lsn, write_lsn, flush_lsn, replay_lsn
     FROM pg_stat_replication ORDER BY client_addr;" \
  > "$UPGRADE_DIR/replication-before.txt"

runuser -u postgres -- "$OLD_BIN/pg_controldata" "$OLD_DATA" \
  > "$UPGRADE_DIR/pg_controldata-before.txt"
cat "$UPGRADE_DIR/source-settings.txt"
```

`lc_collate` and `lc_ctype` are queried from `pg_database` rather than with
`SHOW`; PostgreSQL 16 and later no longer expose them as server GUCs.

Run these on the leader while the source-major cluster is still running:

```bash

apt-get update
apt-get install -y \
  postgresql-18 postgresql-client-18 postgresql-contrib-18 \
  postgresql-server-dev-18 postgresql-18-cron

# Install PG18 builds for every shared-library extension listed in extensions.txt.

# apt-get install -y postgresql-18-partman postgresql-18-repack

"$NEW_BIN/postgres" --version
```

rollback copy once PG18 has started.

## 7. Run `pg_upgrade --check` on the former leader

```bash
# CONTAINER — former leader only
set -o pipefail
runuser -u postgres -- bash -lc \
  "cd /var/lib/postgresql && '$NEW_BIN/pg_upgrade' --check --link \
    --old-bindir='$OLD_BIN' --new-bindir='$NEW_BIN' \
    --old-datadir='$OLD_DATA' --new-datadir='$NEW_DATA' \
    --username=postgres --jobs=2" \
  2>&1 | tee "$UPGRADE_DIR/pg-upgrade-check.log"
```

Resolve every error before the real upgrade. In particular, install a PG18
package for every extension that has a shared library. `plpgsql` is built into
PostgreSQL and is not a separate contrib package; `pg_stat_statements` and
similar extensions are supplied by `postgresql-contrib-18`.

## 8. Upgrade the former leader with `pg_upgrade --link`

`pg_upgrade` must run only on the former leader, with the source-major cluster stopped and the
initialized PG18 target empty apart from `initdb` output:

```bash
# CONTAINER — former leader only
set -o pipefail
runuser -u postgres -- bash -lc \
  "cd /var/lib/postgresql && '$NEW_BIN/pg_upgrade' --link \
    --old-bindir='$OLD_BIN' --new-bindir='$NEW_BIN' \
    --old-datadir='$OLD_DATA' --new-datadir='$NEW_DATA' \
    --username=postgres --jobs=2" \
  2>&1 | tee "$UPGRADE_DIR/pg-upgrade.log"
```

Save the output. A successful run prints `Upgrade Complete` and creates
`update_extensions.sql` and `delete_old_cluster.sh` in `/var/lib/postgresql`.
If it fails before linking begins, reinitialize the PG18 target before retrying.
If it fails after linking begins, do not assume the PG15 directory is usable;
restore the former leader from the separate backup before attempting rollback.

Do not run `delete_old_cluster.sh`. The old and new directories share hard-linked
files in link mode, and the old directory is retained only for the rsync step and
for inspection until the acceptance decision.

## 9. Point Patroni and pgBackRest at PG18

Repeat this block on **every** primary-cluster node. It updates local runtime
configuration without running the destructive installation prechecks. On the
former leader, PG18 now exists. On a replica, this only changes the local
configuration; do not start Patroni or PostgreSQL on any replica yet. The
`sed` commands replace the dynamically discovered source paths; inspect the
files if they were already changed.

```bash
# CONTAINER — repeat on every primary-cluster node
sed -i \
  -e "s#${OLD_BIN}#${NEW_BIN}#g" \
  -e "s#${OLD_DATA}#${NEW_DATA}#g" \
  /etc/patroni/patroni.yml

sed -i \
  "s#${OLD_DATA}#${NEW_DATA}#g" \
  /etc/pgbackrest/pgbackrest.conf

grep -E 'data_dir:|bin_dir:|pg1-path=' \
  /etc/patroni/patroni.yml /etc/pgbackrest/pgbackrest.conf
```

If the old data directory contains Patroni's dynamic configuration file, copy
it to the upgraded primary if `pg_upgrade` did not already copy it. Review it
first; it preserves DCS-stored Patroni settings when the old initialization
state is removed:

```bash
# CONTAINER — former leader only
if [ -f "$OLD_DATA/patroni.dynamic.json" ] && \
   [ ! -f "$NEW_DATA/patroni.dynamic.json" ]; then
  cp -p "$OLD_DATA/patroni.dynamic.json" "$NEW_DATA/patroni.dynamic.json"
  chown postgres:postgres "$NEW_DATA/patroni.dynamic.json"
fi
```

The former leader's PG18 data directory now exists. On each replica, leave the
source-major directory in place for the hard-link-aware rsync comparison and
ensure `/var/lib/postgresql/18/main` does not contain a package-created cluster.
Do not start any PostgreSQL server until the rsync step has completed on every
replica.


## 11. Remove the old Patroni initialization state from etcd

The PG18 cluster has a new PostgreSQL system identifier. With Patroni stopped
on every node and etcd still healthy, remove the old cluster state once from
the former leader's container:

```bash
# CONTAINER — former leader only; Patroni must be stopped everywhere
patronictl -c /etc/patroni/patroni.yml remove "$CLUSTER_NAME"
```

Confirm the command targets exactly `docpg-cls1`, then type the confirmation
phrase requested by Patroni. This removes the old Patroni cluster keys, not
the etcd member database. It does not delete PostgreSQL data. The `remove`
subcommand is intentionally interactive in Patroni 4.x and does not support a
`--force` option. If Patroni additionally asks for the leader name, enter the
former leader recorded in step 2.

Do not use an etcd `rm -rf` operation or delete the entire etcd data directory.
The etcd cluster is still needed for the new Patroni DCS.

## 12. Synchronize replicas with `rsync` before starting any server

This is the PostgreSQL documented standby-upgrade procedure for a `--link`
upgrade. **Do not start PG18 on the former leader or any replica until all
replicas have been synchronized.** The source and target directory trees must
have the same parent layout on every node:

```text
/var/lib/postgresql/15/main   # old cluster
/var/lib/postgresql/18/main   # new cluster
```

The current Docker image includes an SSH server, but Ansible normally uses
`docker exec` and does not configure inter-container SSH keys. Set up a
temporary internal rsync transport for this maintenance window. Do not expose
SSH or rsync ports on the Mac host.

### HOST — prepare temporary SSH transport

Set `LEADER` to the former leader and run from the Mac. The generated private
key remains inside the leader container; only its public key is installed on
the replicas.

```bash
# HOST
LEADER=docpg-cls1-pg1
for n in docpg-cls1-pg2 docpg-cls1-pg3; do
  docker exec "$n" apt-get update
  docker exec "$n" apt-get install -y rsync openssh-server
  docker exec "$n" systemctl start ssh
  docker exec "$n" install -d -o ansible -g ansible -m 700 /home/ansible/.ssh
  docker exec "$n" touch /home/ansible/.ssh/authorized_keys
  docker exec "$n" chown ansible:ansible /home/ansible/.ssh/authorized_keys
  docker exec "$n" chmod 600 /home/ansible/.ssh/authorized_keys
done

docker exec "$LEADER" apt-get update
docker exec "$LEADER" apt-get install -y rsync openssh-client
docker exec "$LEADER" systemctl start ssh
docker exec "$LEADER" install -d -m 700 /root/.ssh
docker exec "$LEADER" sh -c \
  "test -f /root/.ssh/pgupgrade_rsync_ed25519 || \
   ssh-keygen -q -t ed25519 -N '' -f /root/.ssh/pgupgrade_rsync_ed25519"

for n in docpg-cls1-pg2 docpg-cls1-pg3; do
  docker exec "$LEADER" cat /root/.ssh/pgupgrade_rsync_ed25519.pub |
    docker exec -i "$n" tee -a /home/ansible/.ssh/authorized_keys >/dev/null
done
```

Test the transport from the leader. Replace an address if the inventory has
different replica members:

```bash
# CONTAINER — former leader
RSYNC_KEY=/root/.ssh/pgupgrade_rsync_ed25519
ssh -i "$RSYNC_KEY" -o StrictHostKeyChecking=no \
  ansible@172.18.0.12 true
ssh -i "$RSYNC_KEY" -o StrictHostKeyChecking=no \
  ansible@172.18.0.13 true
```

The remote `rsync` process runs through passwordless sudo so that ownership,
permissions, and hard links are preserved. Stop if either SSH test fails.

### CONTAINER — prepare each replica's target tree

Run this on each replica while all PostgreSQL and Patroni services remain
stopped. Do not move the old PG15 tree: rsync needs it as the destination-side
reference for recreating the hard-link relationships.

```bash
# CONTAINER — each replica
systemctl stop patroni pgbouncer haproxy keepalived
runuser -u postgres -- "$OLD_BIN/pg_ctl" -D "$OLD_DATA" status
test $? -eq 3

NEW_ROOT="$(dirname "$NEW_DATA")"
if [ -d "$NEW_ROOT" ] && [ -n "$(find "$NEW_ROOT" -mindepth 1 -print -quit 2>/dev/null)" ]; then
  TARGET_BACKUP="/var/lib/postgresql/upgrade-backups/pg${TARGET_MAJOR}-target-before-rsync-$(date '+%Y-%m-%d__%H_%M_%S')"
  install -d -o postgres -g postgres -m 700 /var/lib/postgresql/upgrade-backups
  mv "$NEW_ROOT" "$TARGET_BACKUP"
  echo "Preserved existing target at $TARGET_BACKUP"
fi
```

If a replica has user tablespaces or `pg_wal` outside the data directory, stop
here and inventory those paths. They require a corresponding rsync operation;
this runbook's commands cover the repository's standard in-data-directory
layout.

### CONTAINER — rsync both directory trees from the former leader

Run from the former leader, once per replica, while **every PostgreSQL server
is still stopped**. First use `--dry-run`; review the file list before running
the real transfer.

```bash
# CONTAINER — former leader; repeat REPLICA_IP for every replica
OLD_ROOT="$(dirname "$OLD_DATA")"
NEW_ROOT="$(dirname "$NEW_DATA")"
RSYNC_KEY=/root/.ssh/pgupgrade_rsync_ed25519
REPLICA_IP=172.18.0.12

rsync --dry-run --archive --delete --hard-links --size-only \
  --no-inc-recursive \
  -e "ssh -i $RSYNC_KEY -o StrictHostKeyChecking=no" \
  --rsync-path="sudo -n rsync" \
  "$OLD_ROOT" "$NEW_ROOT" \
  "ansible@${REPLICA_IP}:/var/lib/postgresql/"

rsync --archive --delete --hard-links --size-only \
  --no-inc-recursive \
  -e "ssh -i $RSYNC_KEY -o StrictHostKeyChecking=no" \
  --rsync-path="sudo -n rsync" \
  "$OLD_ROOT" "$NEW_ROOT" \
  "ansible@${REPLICA_IP}:/var/lib/postgresql/"
```

The `--hard-links` option is essential: it lets rsync reproduce the links that
`pg_upgrade --link` created between the PG15 and PG18 trees. `--delete` applies
to the PG15 and PG18 destination trees only; it does not delete the replica's
old PG15 directory. If a transfer fails, keep all servers stopped and rerun it
after correcting the transport or filesystem problem.

After every replica has been synchronized, verify the target version and file
ownership without starting PostgreSQL:

```bash
# HOST — repeat for each replica
docker exec docpg-cls1-pg2 test "$(docker exec docpg-cls1-pg2 cat /var/lib/postgresql/18/main/PG_VERSION)" = 18
docker exec docpg-cls1-pg3 test "$(docker exec docpg-cls1-pg3 cat /var/lib/postgresql/18/main/PG_VERSION)" = 18
docker exec docpg-cls1-pg2 ls -ld /var/lib/postgresql/18/main
docker exec docpg-cls1-pg3 ls -ld /var/lib/postgresql/18/main
```

Do not create `standby.signal` or copy `primary_conninfo` by hand at this
stage. Once the rsynced PG18 data directory is present, Patroni will configure
the replica relationship when each member is started. If the local Patroni
version does not do so, stop and inspect its generated recovery configuration;
do not use `patronictl reinit` as a fallback in this procedure.

## 13. Start the upgraded primary

Start Patroni only on the former leader first. Patroni will create the new
cluster state in etcd from the updated local configuration and the upgraded
PG18 data directory.

```bash
# CONTAINER — former leader only
systemctl start patroni
systemctl is-active patroni

for i in $(seq 1 30); do
  curl -sf http://127.0.0.1:8008/primary >/dev/null && break
  sleep 2
done
curl -sf http://127.0.0.1:8008/primary
runuser -u postgres -- "$NEW_BIN/psql" -h 127.0.0.1 -U postgres -x -c \
  "SELECT version(), current_setting('data_directory') AS data_directory;"
runuser -u postgres -- "$NEW_BIN/psql" -h 127.0.0.1 -U postgres -Atqc \
  "SELECT name || '=' || setting
     FROM pg_settings
    WHERE name IN ('server_version', 'archive_mode', 'archive_command', 'wal_level')
    ORDER BY name;"
```

The response must show a PostgreSQL 18 primary and
`/var/lib/postgresql/18/main`. If Patroni does not become leader, stop it and
inspect `journalctl -u patroni`; do not start the replicas blindly.

## 14. Validate pgBackRest and create a PG18 backup

Run these on the upgraded primary. The offline `stanza-upgrade` in step 10
updated the stanza metadata while retaining the old repository history. Now
verify the live archive configuration and create a new full backup for replica
cloning and rollback.

```bash
# CONTAINER — upgraded primary only
runuser -u postgres -- pgbackrest --stanza="$STANZA_NAME" check
runuser -u postgres -- pgbackrest --stanza="$STANZA_NAME" \
  --type=full --log-level-console=info backup
runuser -u postgres -- pgbackrest --stanza="$STANZA_NAME" info
```

Do not expire the source-major backups yet. If `stanza-upgrade` or `check` reports a
path/system-ID mismatch, stop and correct `/etc/pgbackrest/pgbackrest.conf`;
do not delete the stanza or repository as a first response.

## 15. Start rsynced replicas one at a time

Do not run `pg_upgrade` or `patronictl reinit` on these nodes. The PG18 data
directories were synchronized in step 12 while all servers were stopped. Start
one replica at a time only after the upgraded primary is healthy. Patroni should
detect the PG18 data directory, configure it to follow the new leader, and
start it in recovery.

```bash
# HOST — one replica at a time
REPLICA=docpg-cls1-pg2
docker exec "$REPLICA" systemctl reset-failed patroni
docker exec "$REPLICA" systemctl start patroni

for i in $(seq 1 90); do
  if docker exec "$REPLICA" curl -sf http://127.0.0.1:8008/replica >/dev/null; then
    echo "$REPLICA is a healthy replica"
    break
  fi
  sleep 2
done

docker exec "$REPLICA" patronictl -c /etc/patroni/patroni.yml list
docker exec "$REPLICA" runuser -u postgres -- /usr/lib/postgresql/18/bin/psql \
  -h 127.0.0.1 -U postgres -Atqc \
  "SELECT version(), pg_is_in_recovery(), current_setting('data_directory');"
```

Repeat the block for `docpg-cls1-pg3` only after `pg2` is shown as `Replica`,
`streaming`, and has acceptable lag. The final `pg_is_in_recovery()` result
must be `t`. If a replica does not start in recovery, stop Patroni immediately,
inspect `journalctl -u patroni` and the generated PostgreSQL configuration, and
do not issue `reinit`; correct the rsync source and target trees instead.

### Diagnostics if a replica does not start

```bash

systemctl stop patroni
journalctl -u patroni -n 100 --no-pager -o cat
runuser -u postgres -- /usr/local/bin/patroni \
```

Use this check before moving to the next replica:

```bash
# CONTAINER — query the current primary or use patronictl from any node
patronictl -c /etc/patroni/patroni.yml list
runuser -u postgres -- "$NEW_BIN/psql" -h 127.0.0.1 -U postgres -Atqc \
  "SELECT version(), pg_is_in_recovery(), current_setting('data_directory');"
```

If the replica does not start in recovery, stop Patroni, inspect
`journalctl -u patroni`, and compare the rsync source and target trees. Do not
enable `reinit_cluster`, run `pg_upgrade` on the replica, or delete its old
PG15 directory as a shortcut.

## 19. Remove the old PostgreSQL binary path from `PATH`

After the PG18 cluster has passed the validation checks and section 18 has
updated Ansible's desired version, remove the source-major binary directory
from the persistent shell environment on every PostgreSQL container. The
`container_env` tag in section 18 normally rewrites these files; this step
explicitly verifies and corrects the result. Replace `15` if the discovered
source major differs from the title of this runbook.

```bash
# CONTAINER — repeat on every primary-cluster node after PG18 validation
OLD_BIN="/usr/lib/postgresql/15/bin"
NEW_BIN="/usr/lib/postgresql/18/bin"

for path_file in \
  /etc/profile.d/pg_env.sh \
  /root/.bashrc \
  /var/lib/postgresql/.bashrc; do
  if [ -f "$path_file" ]; then
    sed -i "s#${OLD_BIN}:#${NEW_BIN}:#g" "$path_file"
  fi
done

PATH=$(printf '%s' "$PATH" | awk -v old="$OLD_BIN" \
  'BEGIN { RS=":"; ORS=":" } $0 != old { print }' | sed 's/:$//')
export PATH
hash -r

case ":$PATH:" in
  *":$OLD_BIN:"*)
    echo "Old PostgreSQL binary path is still present in PATH" >&2
    exit 1
    ;;
esac
test "$(command -v psql)" = "$NEW_BIN/psql"
psql --version
grep -Hn "$OLD_BIN\|$NEW_BIN" \
  /etc/profile.d/pg_env.sh /root/.bashrc /var/lib/postgresql/.bashrc \
  2>/dev/null || true
```

Open a new shell, or source the updated profile files, before running any
unversioned PostgreSQL client command. Rollback commands in the next section
continue to use explicit versioned paths and do not depend on `PATH`.

## 20. Rollback before acceptance

With `--link`, rollback after PG18 has started is **not** a simple switch back
to `$OLD_DATA`: PG18 may have modified files shared with that directory. If
rollback is required after the new primary starts, restore the former leader's
PG15 data directory from the separate physical backup or filesystem snapshot
created before the upgrade. Writes accepted by PG18 are not present in that
PG15 backup.

### HOST — stop the PG18 services on every node

```bash
# HOST
for n in docpg-cls1-pg1 docpg-cls1-pg2 docpg-cls1-pg3; do
  docker exec "$n" systemctl stop patroni pgbouncer haproxy keepalived
done
```

### CONTAINER — restore Patroni paths and the PG15 primary

Restore the former leader's PG15 data directory from the separate physical
backup or snapshot. Do not start the hard-linked `$OLD_DATA` after PG18 has
started. On each node, restore the local Patroni and pgBackRest paths to the
source major using the values recorded in step 1, then remove the PG18 Patroni
DCS state and start only the restored PG15 primary first.

```bash
# CONTAINER — repeat path restoration on every node
sed -i \
  -e "s#${NEW_BIN}#${OLD_BIN}#g" \
  -e "s#${NEW_DATA}#${OLD_DATA}#g" \
  /etc/patroni/patroni.yml
sed -i \
  "s#${NEW_DATA}#${OLD_DATA}#g" \
  /etc/pgbackrest/pgbackrest.conf
```

On the former leader, restore the PG15 data directory using the approved
backup/snapshot procedure. The exact restore command depends on the backup
system and is intentionally not guessed here:

```bash
# CONTAINER — former leader; replace with the approved restore operation
systemctl stop patroni
test ! -e "$OLD_DATA" || mv "$OLD_DATA" \
  "/var/lib/postgresql/upgrade-backups/pg${OLD_MAJOR}-hardlink-copy-not-for-use"
# Restore a complete PG15 data directory to "$OLD_DATA" from the backup/snapshot.
test -f "$OLD_DATA/PG_VERSION"
test "$(cat "$OLD_DATA/PG_VERSION")" = "$OLD_MAJOR"
chown -R postgres:postgres "$OLD_DATA"
```

The old PG15 directories on the former replicas were not overwritten by the
rsync command. Verify them and use them only after the former leader has been
restored; if a replica's PG15 directory is damaged, restore it from the same
pre-upgrade backup.

On the former leader:

```bash
# CONTAINER — former leader only
patronictl -c /etc/patroni/patroni.yml remove "$CLUSTER_NAME"
systemctl start patroni
curl -sf http://127.0.0.1:8008/primary
runuser -u postgres -- "$OLD_BIN/psql" -h 127.0.0.1 -U postgres -x -c \
  "SELECT version(), current_setting('data_directory');"
```

Start the preserved source-major replica directories one at a time after the old
primary is healthy. Do not leave a replica using a PG18 data directory with a
source-major Patroni configuration. Validate the old cluster before restoring
traffic.

### HOST — restore Ansible's version on rollback

On the Mac, set `postgresql_version: "15"` in `vars/dba_vars.yml`. Do not run
the full installer; review any targeted configuration run before applying it.

## 21. Cleanup after acceptance

After the application has passed its acceptance period, backups are verified,
and rollback is no longer required:

1. Record Patroni, etcd, pgBackRest, application, and statistics evidence.
2. Confirm the active data directory is `/var/lib/postgresql/18/main`.
3. Confirm a new PG18 full backup is restorable.
4. Retain the logical dumps and old source-major pgBackRest backups according
   to policy.
5. Only then remove the source-major directories and old package data. In link
   mode, remove the old directory only after confirming PG18 is healthy; its
   files may be shared with the active PG18 directory.
6. Optionally remove unused source-major packages after checking other services do not
   depend on them.
7. Remove the temporary rsync SSH key and its authorized-key entries from all
   replicas.

`pg_upgrade` generated `delete_old_cluster.sh` in `/var/lib/postgresql`. It is
deliberately not run by this document because it is irreversible. If the final
decision is to use it, inspect it first and run it only on the former leader
after acceptance:

```bash
# CONTAINER — former leader only, after rollback is no longer required
cd /var/lib/postgresql
runuser -u postgres -- ./delete_old_cluster.sh
```

Remove the temporary rsync transport after the upgrade is accepted:

```bash
# HOST
docker exec docpg-cls1-pg1 rm -f /root/.ssh/pgupgrade_rsync_ed25519 /root/.ssh/pgupgrade_rsync_ed25519.pub
for n in docpg-cls1-pg2 docpg-cls1-pg3; do
  docker exec "$n" sed -i '/pgupgrade_rsync_ed25519/d' /home/ansible/.ssh/authorized_keys
done
```

## Optional standby/DR Patroni cluster

The optional `standby_cluster` is a separate Patroni cluster with its own
etcd membership and upgrade timing. Do not upgrade its PostgreSQL binaries
while it is still streaming from the source-major primary and do not point it
at the PG18 primary until the primary cluster has been accepted.

For a multi-node standby cluster, repeat this runbook against that cluster only
after the primary cluster is stable: stop its Patroni members while retaining
etcd quorum, upgrade only its former leader, remove only its own Patroni scope,
start its PG18 leader, and rebuild its replicas. For a single-node DR standby,
preserve its source-major data and follow the same former-leader procedure, but
account for the DR outage and re-establish the standby relationship after the
primary upgrade.
