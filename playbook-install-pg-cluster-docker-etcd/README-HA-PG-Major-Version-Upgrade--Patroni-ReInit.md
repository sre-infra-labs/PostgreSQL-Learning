# Patroni + etcd PostgreSQL Major-Version Upgrade: 15 to 18

This runbook upgrades the PostgreSQL **primary Patroni cluster** in this
repository from PostgreSQL 15 to PostgreSQL 18. It supports a cluster with two
or more PostgreSQL/Patroni nodes and uses `pg_upgrade --copy` on the former
Patroni leader. Replicas are not upgraded with `pg_upgrade`; Patroni rebuilds
them from the upgraded primary.

The procedure has a planned outage. It is intentionally conservative because
the PostgreSQL system identifier changes during a major upgrade and physical
replication cannot continue between PostgreSQL 15 and PostgreSQL 18.

Official references:

- [Patroni: Major Upgrade of PostgreSQL Version](https://patroni.readthedocs.io/en/latest/existing_data.html#major-upgrade-of-postgresql-version)
- [PostgreSQL: pg_upgrade](https://www.postgresql.org/docs/18/pgupgrade.html)

## Scope and topology

This document covers the `primary_cluster` group. In the current inventory it
contains:

| Node | Address | Purpose |
| --- | --- | --- |
| `docpg-cls1-pg1` | `172.18.0.11` | Patroni member; designed leader |
| `docpg-cls1-pg2` | `172.18.0.12` | Patroni member; synchronous standby |
| `docpg-cls1-pg3` | `172.18.0.13` | Patroni member; asynchronous `nosync` replica |

Roles are dynamic. Never assume `pg1` is the leader; identify the current
leader with `patronictl` before stopping services.

Every PostgreSQL container also runs one member of the three-member etcd DCS,
plus Patroni, pgBackRest, pgBouncer, HAProxy, and Keepalived. PostgreSQL data
and logs are in per-node Docker volumes. The pgBackRest repository is the
shared `pg-backups` volume.

The runbook assumes the standard paths generated by this role:

| Item | Value |
| --- | --- |
| Old PostgreSQL data | Discovered from the running source cluster |
| New PostgreSQL data | `/var/lib/postgresql/18/main` |
| Old binaries | Derived from the discovered source major |
| New binaries | `/usr/lib/postgresql/18/bin` |
| Patroni config | `/etc/patroni/patroni.yml` |
| pgBackRest config | `/etc/pgbackrest/pgbackrest.conf` |
| Patroni scope / pgBackRest stanza | `docpg-cls1` |
| PostgreSQL service manager | `patroni.service` |
| DCS | etcd on ports `2379` and `2380` |

If your inventory uses different names, IPs, versions, paths, or stanza names,
replace the examples and verify them before proceeding.

## Critical warnings

1. **This is a planned outage.** Stop application writes and drain connection
   pools before the maintenance window.
2. **Do not run `pg_upgrade` on a physical Patroni replica.** PostgreSQL does
   not support that operation. Rebuild each replica from the upgraded primary.
3. Stop Patroni on every PostgreSQL node before upgrading the former leader.
   Keep etcd running and maintain quorum. For a two-member etcd cluster, both
   members must remain available; for three members, do not take two etcd
   members down at once.
4. Do not run the installation playbook with `-e reinit_cluster=true`. The
   role removes the configured PostgreSQL data directory, etcd data, and
   Patroni keys. That is not the upgrade procedure.
5. Do not run `playbook-cleanup.yml`, remove Docker volumes, or run
   `delete_old_cluster.sh` before acceptance.
6. Do not start the old and new PostgreSQL clusters at the same time on one
   node. Both clusters must never use the same port or data directory.
7. `pg_upgrade --copy` needs enough free space for the PG18 target and the
   preserved source-major cluster. The old source is the rollback copy.
8. The cluster DCS state must be removed or its `initialize` key cleared after
   the PG18 primary is prepared. The upgraded cluster has a new system ID;
   retaining the old Patroni initialization key prevents a clean start.

## Execution context

Commands marked **HOST** run in a terminal on the Mac. Commands marked
**CONTAINER** run inside an interactive container shell as `root`. The host has
no mapped PostgreSQL, Patroni, or etcd ports, so container commands must not be
run directly on the Mac.

Enter one container at a time from the Mac when a step says to use a container
shell:

```bash
# HOST — use the node currently identified as the leader
docker exec -it -u root docpg-cls1-pg1 bash
```

For a step that applies to every node, open a separate shell for each node and
run the same **CONTAINER** block in each shell. Do not paste `docker exec`
inside a container shell.

`runuser -u postgres --` means “run the following command as the PostgreSQL OS
user.” The examples assume the interactive shell starts as `root`.

### CONTAINER — discover the source version and define variables

Run this while the existing PostgreSQL cluster is still running. The source
major and data directory are discovered from the live server, so this works
whether the source is PG14, PG15, or another older supported major. Do not edit
the Ansible version variable yet. Keep this shell open, or record the printed
values for any later shell used during rollback.

```bash
# CONTAINER
TARGET_MAJOR=18
# This document is executed in an interactive shell. Do not leave errexit or
# nounset enabled: later checks intentionally use non-zero statuses, including
# `pg_ctl status` returning 3 when the source server is stopped.
set +e
set +u

OLD_VERSION_NUM=$(runuser -u postgres -- psql -h 127.0.0.1 -U postgres -Atqc \
  "SHOW server_version_num;")
case "$OLD_VERSION_NUM" in
  ''|*[!0-9]*)
    echo "Unable to discover a numeric PostgreSQL server_version_num: $OLD_VERSION_NUM" >&2
    echo "Stop here and verify that the source PostgreSQL server is running." >&2
    OLD_VERSION_NUM=0
    ;;
esac
OLD_MAJOR=$((OLD_VERSION_NUM / 10000))
OLD_DATA=$(runuser -u postgres -- psql -h 127.0.0.1 -U postgres -Atqc \
  "SHOW data_directory;")

test "$OLD_MAJOR" -lt "$TARGET_MAJOR"
test -d "$OLD_DATA"
test -f "$OLD_DATA/PG_VERSION"

NEW_DATA="/var/lib/postgresql/${TARGET_MAJOR}/main"
OLD_BIN="/usr/lib/postgresql/${OLD_MAJOR}/bin"
NEW_BIN="/usr/lib/postgresql/${TARGET_MAJOR}/bin"
CLUSTER_NAME="docpg-cls1"
STANZA_NAME="docpg-cls1"
UPGRADE_DIR="/var/lib/postgresql/upgrade-backups/pg${OLD_MAJOR}-to-pg${TARGET_MAJOR}-$(date '+%Y-%m-%d__%H_%M_%S')"

printf 'source=%s target=%s old_data=%s new_data=%s\n' \
  "$OLD_MAJOR" "$TARGET_MAJOR" "$OLD_DATA" "$NEW_DATA"
test -x "$OLD_BIN/postgres"
test ! -e "$NEW_DATA" || test -z "$(ls -A "$NEW_DATA" 2>/dev/null)"
install -d -o postgres -g postgres -m 700 "$UPGRADE_DIR"
```

The `test` for `NEW_DATA` must pass. If it does not, stop and determine
whether it is an automatically-created empty PG18 cluster. Never overwrite a
non-empty target without verifying its ownership and purpose.

## 2. Identify the Patroni leader and baseline cluster health

### HOST — find the current leader

Run this from the Mac. Try any healthy primary node:

### CONTAINER — baseline checks on the current leader

Enter the leader container and run:

```bash
# CONTAINER — run on the current leader
runuser -u postgres -- "$OLD_BIN/psql" -h 127.0.0.1 -U postgres -Atqc \
  "SHOW server_version; SHOW server_version_num; SHOW data_directory;" \
  > "$UPGRADE_DIR/source-settings.txt"
runuser -u postgres -- "$OLD_BIN/psql" -h 127.0.0.1 -U postgres -Atqc \
  "SELECT datname, datcollate, datctype FROM pg_database ORDER BY 1;" \
  >> "$UPGRADE_DIR/source-settings.txt"

runuser -u postgres -- "$OLD_BIN/psql" -h 127.0.0.1 -U postgres -P pager=off -c \
  "SELECT datname, pg_size_pretty(pg_database_size(datname)) AS size
     FROM pg_database ORDER BY pg_database_size(datname) DESC;" \
  > "$UPGRADE_DIR/database-sizes.txt"

runuser -u postgres -- "$OLD_BIN/psql" -h 127.0.0.1 -U postgres -P pager=off -c \
  "SELECT extname, extversion FROM pg_extension ORDER BY 1;" \
  > "$UPGRADE_DIR/extensions.txt"

runuser -u postgres -- "$OLD_BIN/psql" -h 127.0.0.1 -U postgres -P pager=off -c \
  "SELECT client_addr, application_name, state, sync_state,
          sent_lsn, write_lsn, flush_lsn, replay_lsn
     FROM pg_stat_replication ORDER BY client_addr;" \
  > "$UPGRADE_DIR/replication-before.txt"

runuser -u postgres -- "$OLD_BIN/pg_controldata" "$OLD_DATA" \
  > "$UPGRADE_DIR/pg_controldata-before.txt"
cat "$UPGRADE_DIR/source-settings.txt"
```

`lc_collate` and `lc_ctype` are queried from `pg_database` rather than with
`SHOW`; PostgreSQL 16 and later no longer expose them as server GUCs.

### HOST — verify every node before the outage

### CONTAINER — logical dumps on the leader

```bash

runuser -u postgres -- "$OLD_BIN/pg_dumpall" --globals-only \
  > "$UPGRADE_DIR/globals.sql"

  > "$UPGRADE_DIR/all-databases.sql"

```

### CONTAINER — pgBackRest backup and integrity checks

Run these on the leader while the source-major cluster is still running:

```bash
# CONTAINER — leader
runuser -u postgres -- pgbackrest --stanza="$STANZA_NAME" check
runuser -u postgres -- pgbackrest --stanza="$STANZA_NAME" --type=full backup
```

Install packages before stopping the cluster where possible. Repeat this

```bash
# CONTAINER — repeat on every primary-cluster node
apt-get update
apt-get install -y \
  postgresql-18 postgresql-client-18 postgresql-contrib-18 \
  postgresql-server-dev-18 postgresql-18-cron

# Install PG18 builds for every shared-library extension listed in extensions.txt.
# Examples, only when those extensions are installed in the source cluster:
# apt-get install -y postgresql-18-partman postgresql-18-repack

"$NEW_BIN/postgres" --version
"$NEW_BIN/pg_upgrade" --version
```

If apt created `/etc/postgresql/18/main` and an empty target cluster, stop and

```bash
pg_dropcluster --stop 18 main
test ! -e "$NEW_DATA" || test -z "$(ls -A "$NEW_DATA" 2>/dev/null)"
```

Do not remove `"$OLD_DATA"` on any node. It is the preserved rollback source.

## 5. Prepare for the maintenance outage

### HOST — stop application traffic

Drain the application and stop external jobs using the cluster. There are no
host port mappings in this setup; the application normally reaches the
Keepalived/HAProxy VIPs inside `lab-network`.

### HOST — stop Patroni-managed traffic services on every node

The following commands execute inside each container but are launched from the
Mac. Keep etcd running; only Patroni and traffic-facing services are stopped.

```bash
# HOST — repeat for every primary-cluster container
for n in docpg-cls1-pg1 docpg-cls1-pg2 docpg-cls1-pg3; do
  docker exec "$n" systemctl stop patroni pgbouncer haproxy keepalived
done
```

### CONTAINER — verify PostgreSQL is stopped and etcd quorum remains

Run in any container shell, after the host loop completes:

```bash
# CONTAINER
systemctl is-active patroni pgbouncer haproxy keepalived || true
runuser -u postgres -- "$OLD_BIN/pg_ctl" -D "$OLD_DATA" status
test $? -eq 3

etcdctl --endpoints=http://172.18.0.11:2379,http://172.18.0.12:2379,http://172.18.0.13:2379 \
  endpoint health
etcdctl --endpoints=http://172.18.0.11:2379,http://172.18.0.12:2379,http://172.18.0.13:2379 \
  member list
```

The `pg_ctl status` command must return exit code 3, meaning the source-major
cluster is stopped.
The etcd health command must show a quorum of healthy members. If etcd has lost
quorum, stop and repair etcd before continuing.

## 6. Initialize the PG18 target on the former leader

Run this **CONTAINER** block only on the former Patroni leader. The locale,
encoding, and checksum settings must match the source values recorded in step
2. This repository normally uses `en_US.UTF-8`, `UTF8`, and data checksums.

```bash
# CONTAINER — former leader only
install -d -o postgres -g postgres -m 700 "$(dirname "$NEW_DATA")"
runuser -u postgres -- "$NEW_BIN/initdb" \
  --pgdata="$NEW_DATA" \
  --encoding=UTF8 \
  --locale=en_US.UTF-8 \
  --data-checksums
test -f "$NEW_DATA/PG_VERSION"
cat "$NEW_DATA/PG_VERSION"
```

If the source baseline differs, stop and reinitialize the empty target with the
source's actual compatible settings. Do not guess a locale.

## 7. Run `pg_upgrade --check` on the former leader

```bash
# CONTAINER — former leader only
set -o pipefail
runuser -u postgres -- bash -lc \
  "cd /var/lib/postgresql && '$NEW_BIN/pg_upgrade' --check --copy \
    --old-bindir='$OLD_BIN' --new-bindir='$NEW_BIN' \
    --old-datadir='$OLD_DATA' --new-datadir='$NEW_DATA' \
    --username=postgres --jobs=2" \
  2>&1 | tee "$UPGRADE_DIR/pg-upgrade-check.log"
```

Resolve every error before the real upgrade. In particular, install a PG18
package for every extension that has a shared library. `plpgsql` is built into
PostgreSQL and is not a separate contrib package; `pg_stat_statements` and
similar extensions are supplied by `postgresql-contrib-18`.

## 8. Upgrade the former leader with `pg_upgrade --copy`

`pg_upgrade` must run only on the former leader, with the source-major cluster stopped and the
initialized PG18 target empty apart from `initdb` output:

```bash
# CONTAINER — former leader only
set -o pipefail
runuser -u postgres -- bash -lc \
  "cd /var/lib/postgresql && '$NEW_BIN/pg_upgrade' --copy \
    --old-bindir='$OLD_BIN' --new-bindir='$NEW_BIN' \
    --old-datadir='$OLD_DATA' --new-datadir='$NEW_DATA' \
    --username=postgres --jobs=2" \
  2>&1 | tee "$UPGRADE_DIR/pg-upgrade.log"
```

Save the output. A successful run prints `Upgrade Complete` and creates
`update_extensions.sql` and `delete_old_cluster.sh` in `/var/lib/postgresql`.
If it fails after consistency checks begin, reinitialize the PG18 target before
retrying. Do not start Patroni until the cause is resolved.

Do not run `delete_old_cluster.sh`. The copied source-major data is required for
rollback.

## 9. Point Patroni and pgBackRest at PG18

Repeat this block on **every** primary-cluster node. It updates local runtime
configuration without running the destructive installation prechecks. The
The `sed` commands replace the dynamically discovered source paths; inspect the
files if they were already changed.

```bash
# CONTAINER — repeat on every primary-cluster node
sed -i \
  -e "s#${OLD_BIN}#${NEW_BIN}#g" \
  -e "s#${OLD_DATA}#${NEW_DATA}#g" \
  /etc/patroni/patroni.yml

sed -i \
  "s#${OLD_DATA}#${NEW_DATA}#g" \
  /etc/pgbackrest/pgbackrest.conf

grep -E 'data_dir:|bin_dir:|pg1-path=' \
  /etc/patroni/patroni.yml /etc/pgbackrest/pgbackrest.conf
```

If the old data directory contains Patroni's dynamic configuration file, copy
it to the upgraded primary if `pg_upgrade` did not already copy it. Review it
first; it preserves DCS-stored Patroni settings when the old initialization
state is removed:

```bash
# CONTAINER — former leader only
if [ -f "$OLD_DATA/patroni.dynamic.json" ] && \
   [ ! -f "$NEW_DATA/patroni.dynamic.json" ]; then
  cp -p "$OLD_DATA/patroni.dynamic.json" "$NEW_DATA/patroni.dynamic.json"
  chown postgres:postgres "$NEW_DATA/patroni.dynamic.json"
fi
```

The former leader's PG18 data directory now exists. On each replica, leave the
source-major directory preserved for rollback but ensure
`/var/lib/postgresql/18/main` does not contain a package-created cluster.
Patroni will create it by cloning.

## 10. Upgrade pgBackRest metadata while PG18 is offline

The new PostgreSQL system identifier and path must be registered in pgBackRest
before the new primary starts archiving. Run `stanza-upgrade` with
`--no-online` because PG18 is not running yet:

```bash
# CONTAINER — former leader only; PG18 must still be offline
runuser -u postgres -- pgbackrest --stanza="$STANZA_NAME" \
  --no-online --log-level-console=info stanza-upgrade
```

Stop if this fails. Do not delete the stanza or repository as a first response.

## 11. Remove the old Patroni initialization state from etcd

The PG18 cluster has a new PostgreSQL system identifier. With Patroni stopped
on every node and etcd still healthy, remove the old cluster state once from
the former leader's container:

```bash
# CONTAINER — former leader only; Patroni must be stopped everywhere
patronictl -c /etc/patroni/patroni.yml remove "$CLUSTER_NAME"
```

Confirm the command targets exactly `docpg-cls1`, then type the confirmation
phrase requested by Patroni. This removes the old Patroni cluster keys, not
the etcd member database. It does not delete PostgreSQL data. The `remove`
subcommand is intentionally interactive in Patroni 4.x and does not support a
`--force` option. If Patroni additionally asks for the leader name, enter the
former leader recorded in step 2.

Do not use an etcd `rm -rf` operation or delete the entire etcd data directory.
The etcd cluster is still needed for the new Patroni DCS.

## 12. Start the upgraded primary

Start Patroni only on the former leader first. Patroni will create the new
cluster state in etcd from the updated local configuration and the upgraded
PG18 data directory.

```bash
# CONTAINER — former leader only
systemctl start patroni
systemctl is-active patroni

for i in $(seq 1 30); do
  curl -sf http://127.0.0.1:8008/primary >/dev/null && break
  sleep 2
done
curl -sf http://127.0.0.1:8008/primary
runuser -u postgres -- "$NEW_BIN/psql" -h 127.0.0.1 -U postgres -x -c \
  "SELECT version(), current_setting('data_directory') AS data_directory;"
runuser -u postgres -- "$NEW_BIN/psql" -h 127.0.0.1 -U postgres -Atqc \
  "SELECT name || '=' || setting
     FROM pg_settings
    WHERE name IN ('server_version', 'archive_mode', 'archive_command', 'wal_level')
    ORDER BY name;"
```

The response must show a PostgreSQL 18 primary and
`/var/lib/postgresql/18/main`. If Patroni does not become leader, stop it and
inspect `journalctl -u patroni`; do not start the replicas blindly.

## 13. Validate pgBackRest and create a PG18 backup

Run these on the upgraded primary. The offline `stanza-upgrade` in step 10
updated the stanza metadata while retaining the old repository history. Now
verify the live archive configuration and create a new full backup for replica
cloning and rollback.

```bash
# CONTAINER — upgraded primary only
runuser -u postgres -- pgbackrest --stanza="$STANZA_NAME" check
runuser -u postgres -- pgbackrest --stanza="$STANZA_NAME" \
  --type=full --log-level-console=info backup
runuser -u postgres -- pgbackrest --stanza="$STANZA_NAME" info
```

Do not expire the source-major backups yet. If `stanza-upgrade` or `check` reports a
path/system-ID mismatch, stop and correct `/etc/pgbackrest/pgbackrest.conf`;
do not delete the stanza or repository as a first response.

## 14. Rebuild replicas one at a time with Patroni

Do not run `pg_upgrade` on these nodes. For each replica, perform the following
sequence separately. Keep at least the upgraded primary and etcd quorum
available throughout.

### CONTAINER — preserve the source-major replica and prepare the PG18 path

Run on one replica, for example `docpg-cls1-pg2`, then repeat for `pg3`:

```bash
# CONTAINER — one replica at a time
REPLICA_BACKUP="/var/lib/postgresql/upgrade-backups/pg${OLD_MAJOR}-replica-before-pg${TARGET_MAJOR}-$(date '+%Y-%m-%d__%H_%M_%S')"
systemctl stop patroni pgbouncer haproxy keepalived

# Any existing PG18 target may be an automatically-created cluster with a
# different system ID. Preserve it and leave the configured target absent so
# Patroni can clone the replica from the upgraded leader.
if [ -e "$NEW_DATA" ]; then
  REPLICA_TARGET_BACKUP="/var/lib/postgresql/upgrade-backups/pg${TARGET_MAJOR}-target-before-reinit-$(date '+%Y-%m-%d__%H_%M_%S')"
  mv "$NEW_DATA" "$REPLICA_TARGET_BACKUP"
  echo "Preserved existing PG${TARGET_MAJOR} target at $REPLICA_TARGET_BACKUP"
fi
mv "$OLD_DATA" "$REPLICA_BACKUP"
install -d -o postgres -g postgres -m 700 "$(dirname "$NEW_DATA")"
```

The two `mv` commands preserve both the old replica and any existing PG18
target for investigation or rollback. They leave the configured PG18 data path
absent. Record both resulting backup paths. Do not delete either directory.

### CONTAINER — start Patroni and wait for the replica to clone

```bash
# CONTAINER — same replica
grep -E '^(scope|name):|data_dir:|bin_dir:|create_replica_methods:' \
  /etc/patroni/patroni.yml
systemctl reset-failed patroni
systemctl start patroni

for i in $(seq 1 60); do
  _patroni_state=$(systemctl is-active patroni 2>/dev/null || true)
  if [ "$_patroni_state" = "active" ] && \
     curl -sf http://127.0.0.1:8008/health >/dev/null; then
    echo "Patroni is active and its REST API is healthy."
    break
  fi
  if [ "$_patroni_state" = "failed" ]; then
    systemctl stop patroni
    echo "Patroni failed to start; inspect the diagnostics below."
    break
  fi
  sleep 2
done
```

Starting the service registers or starts the member, but an existing Patroni
member can remain `stopped` after its old data directory has been replaced.
If systemd restarts it repeatedly, stop the service before inspecting the real
error. Check the local configuration, target directory, and logs:

```bash
# CONTAINER — same replica
systemctl is-active patroni || true
curl -sf http://127.0.0.1:8008/health && echo
systemctl status patroni --no-pager || true
journalctl -u patroni -n 100 --no-pager -o cat
runuser -u postgres -- /usr/local/bin/patroni \
  --validate-config /etc/patroni/patroni.yml --ignore-listen-port
ls -ld "$NEW_DATA"
test -f "$NEW_DATA/PG_VERSION" && cat "$NEW_DATA/PG_VERSION"
test -x "$NEW_BIN/postgres"
```

If `patronictl list` still shows this member as `stopped`, explicitly request a
reinitialization from the upgraded leader. `--force` is safe here only because
the target is the new PG18 replica directory and the old source directory was
preserved in step 14:

```bash
# CONTAINER — run from any healthy Patroni container; one replica at a time
patronictl -c /etc/patroni/patroni.yml reinit \
  "$CLUSTER_NAME" "$(hostname)" --wait --force
```

Use the exact member name shown by `patronictl list` instead of `$(hostname)` if
they differ. The command removes the failed PG18 target and invokes the
configured `basebackup` method from the upgraded primary. Do not use this
command against the upgraded leader. If Patroni cannot stay running, fix the
configuration or startup error shown by `journalctl` first; `reinit` requires a
live Patroni REST API on the target member.

After `reinit` completes, wait for the member to become healthy:

```bash
# CONTAINER — same replica
for i in $(seq 1 90); do
  if curl -sf http://127.0.0.1:8008/replica >/dev/null && \
     runuser -u postgres -- "$NEW_BIN/psql" -h 127.0.0.1 -U postgres -Atqc \
       "SELECT pg_is_in_recovery();" | grep -qx t; then
    echo "Replica is accepting read traffic and is in recovery."
    break
  fi
  sleep 2
done
```

The current `vars/dba_vars.yml` configures Patroni's `basebackup` method (the
replicas do not have a local pgBackRest repository). Patroni therefore clones
the new replica from the upgraded primary with `pg_basebackup`. Do not move to
the next replica until this node is `Replica`/`streaming` and lag is acceptable:

```bash
# CONTAINER — query the current primary or use patronictl from any node
patronictl -c /etc/patroni/patroni.yml list
runuser -u postgres -- "$NEW_BIN/psql" -h 127.0.0.1 -U postgres -Atqc \
  "SELECT version(), pg_is_in_recovery(), current_setting('data_directory');"
```

If cloning fails, stop Patroni on that replica, inspect
`journalctl -u patroni` and pgBackRest logs, and fix the cause. Do not enable
`reinit_cluster` in the installation role as a shortcut.

If the log contains `system ID mismatch`, the PG18 target still belongs to a
different initialized cluster. Stop Patroni, move that exact target directory
aside, and start Patroni again; do not run `pg_upgrade` on the replica:

```bash
# CONTAINER — affected replica only
systemctl stop patroni
MISMATCHED_TARGET="/var/lib/postgresql/upgrade-backups/pg${TARGET_MAJOR}-mismatched-target-$(date '+%Y-%m-%d__%H_%M_%S')"
mv "$NEW_DATA" "$MISMATCHED_TARGET"
install -d -o postgres -g postgres -m 700 "$(dirname "$NEW_DATA")"
systemctl reset-failed patroni
systemctl start patroni
```

Once the target path is absent, Patroni can bootstrap the member with the
configured `basebackup` method. Wait for the REST health endpoint and
`Replica`/`running` state before proceeding.

## 15. Restore traffic services and validate the HA cluster

After every replica has joined and the intended synchronous standby is
streaming, start the traffic services on all nodes. Keepalived and HAProxy
health checks will move the VIPs according to Patroni roles.

### HOST — start services on every node

```bash
# HOST
for n in docpg-cls1-pg1 docpg-cls1-pg2 docpg-cls1-pg3; do
  docker exec "$n" systemctl start pgbouncer haproxy keepalived
done
```

### HOST — final cluster checks

```bash
# HOST
docker exec docpg-cls1-pg1 patronictl -c /etc/patroni/patroni.yml list
docker exec docpg-cls1-pg1 etcdctl \
  --endpoints=http://172.18.0.11:2379,http://172.18.0.12:2379,http://172.18.0.13:2379 \
  endpoint health
docker exec docpg-cls1-pg1 pgbackrest --stanza=docpg-cls1 check
```

Verify all of the following before reopening application traffic:

- exactly one Patroni `Leader` is running PostgreSQL 18;
- every intended replica is `streaming` and has acceptable lag;
- the configured synchronous standby is `sync` (if synchronous mode is used);
- etcd has quorum and all expected members are healthy;
- the primary and replica VIPs are assigned to the expected nodes;
- HAProxy write/read backends are healthy;
- pgBouncer accepts connections and points at the current primary;
- representative application login, read, write, and transaction tests pass.

## 16. Apply extension updates and refresh statistics

`pg_upgrade` may generate `update_extensions.sql`. Run it once with the PG18
`psql` binary from the directory where `pg_upgrade` was executed. The generated
file normally contains the required database connections.

### CONTAINER — upgraded primary

```bash
# CONTAINER — upgraded primary
cd /var/lib/postgresql
if [ -s update_extensions.sql ]; then
  runuser -u postgres -- "$NEW_BIN/psql" -h 127.0.0.1 -U postgres \
    -d postgres -f update_extensions.sql
fi

runuser -u postgres -- "$NEW_BIN/vacuumdb" -h 127.0.0.1 -U postgres \
  --all --analyze-in-stages --missing-stats-only --jobs=2
runuser -u postgres -- "$NEW_BIN/vacuumdb" -h 127.0.0.1 -U postgres \
  --all --analyze-only --jobs=2
```

Use the versioned PG18 binaries explicitly. The unversioned Debian/Ubuntu
`psql`/`vacuumdb` wrappers can still select the source-major cluster and can
reject options that are not available in the source version.


## 18. Rollback before acceptance

Rollback is possible only while the preserved source-major primary is available
and no unrecoverable writes have been accepted by PG18. Writes made only to
PG18 do not exist in the preserved source cluster.

### HOST — stop the PG18 services on every node

```bash
# HOST
for n in docpg-cls1-pg1 docpg-cls1-pg2 docpg-cls1-pg3; do
  docker exec "$n" systemctl stop patroni pgbouncer haproxy keepalived
done
```

### CONTAINER — restore Patroni paths and start the preserved source primary

On the former leader, the old cluster remains at `$OLD_DATA`. On every node,
restore the local Patroni and pgBackRest paths to the source major. Use the
`OLD_MAJOR`, `OLD_DATA`, and `OLD_BIN` values recorded in step 1; do not
rediscover them from the currently running PG18 cluster. On each replica,
restore its recorded `REPLICA_BACKUP` directory to `$OLD_DATA` before starting
Patroni. Then remove the PG18 Patroni DCS state and start only the old primary
first.

```bash
# CONTAINER — repeat path restoration on every node
sed -i \
  -e "s#${NEW_BIN}#${OLD_BIN}#g" \
  -e "s#${NEW_DATA}#${OLD_DATA}#g" \
  /etc/patroni/patroni.yml
sed -i \
  "s#${NEW_DATA}#${OLD_DATA}#g" \
  /etc/pgbackrest/pgbackrest.conf
```

On each former replica, after the path restoration block and before starting
Patroni, use the exact backup path recorded in step 14:

```bash
# CONTAINER — former replica; use that node's recorded path
test -d "$REPLICA_BACKUP"
test ! -e "$OLD_DATA"
mv "$REPLICA_BACKUP" "$OLD_DATA"
chown -R postgres:postgres "$OLD_DATA"
```

On the former leader:

```bash
# CONTAINER — former leader only
patronictl -c /etc/patroni/patroni.yml remove "$CLUSTER_NAME"
systemctl start patroni
curl -sf http://127.0.0.1:8008/primary
runuser -u postgres -- "$OLD_BIN/psql" -h 127.0.0.1 -U postgres -x -c \
  "SELECT version(), current_setting('data_directory');"
```

Start the preserved source-major replica directories one at a time after the old
primary is healthy. Do not leave a replica using a PG18 data directory with a
source-major Patroni configuration. Validate the old cluster before restoring
traffic.

### HOST — restore Ansible's version on rollback

On the Mac, set `postgresql_version: "15"` in `vars/dba_vars.yml`. Do not run
the full installer; review any targeted configuration run before applying it.

## 19. Cleanup after acceptance

After the application has passed its acceptance period, backups are verified,
and rollback is no longer required:

1. Record Patroni, etcd, pgBackRest, application, and statistics evidence.
2. Confirm the active data directory is `/var/lib/postgresql/18/main`.
3. Confirm a new PG18 full backup is restorable.
4. Retain the logical dumps and old source-major pgBackRest backups according
   to policy.
5. Only then remove the preserved source-major directories and old package data.
6. Optionally remove unused source-major packages after checking other services do not
   depend on them.

`pg_upgrade` generated `delete_old_cluster.sh` in `/var/lib/postgresql`. It is
deliberately not run by this document because it is irreversible. If the final
decision is to use it, inspect it first and run it only on the former leader
after acceptance:

```bash
# CONTAINER — former leader only, after rollback is no longer required
cd /var/lib/postgresql
runuser -u postgres -- ./delete_old_cluster.sh
```

## Optional standby/DR Patroni cluster

The optional `standby_cluster` is a separate Patroni cluster with its own
etcd membership and upgrade timing. Do not upgrade its PostgreSQL binaries
while it is still streaming from the source-major primary and do not point it
at the PG18 primary until the primary cluster has been accepted.

For a multi-node standby cluster, repeat this runbook against that cluster only
after the primary cluster is stable: stop its Patroni members while retaining
etcd quorum, upgrade only its former leader, remove only its own Patroni scope,
start its PG18 leader, and rebuild its replicas. For a single-node DR standby,
preserve its source-major data and follow the same former-leader procedure, but
account for the DR outage and re-establish the standby relationship after the
primary upgrade.
